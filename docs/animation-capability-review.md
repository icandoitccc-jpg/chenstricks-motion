# Animation Capability Technical Review

> 2026-09-21 · 基于已验证技术栈（Remotion 4.0.526 + React + GitHub Actions 2vCPU/7.8GB + Q4 输出基准）的技术侧评估。**本文只做评估，不含实现。**

## 实测性能基线（评估所有成本问题的锚点）

10s/1080p30 成片云端渲染 ≈ 15–20s（Q4 基准），峰值内存 2.4GB，job 墙钟 < 70s。使用量 ≤ 几十条/月。
**含义：即使场景复杂度提升 3–5 倍，仍在「10–20 分钟可接受」的宽松区间内，内存余量 3 倍以上。性能不是 V1 的约束，简单与稳定才是。**

---

### 1. Remotion 能稳定实现的基础动画能力

PoC 已实跑验证：淡入淡出、位移、缩放/Pop（spring 物理）、悬浮循环、描边强调、下划线/直线生长（clip-path reveal）、多元素顺序出现。
同类可直接推导且同样稳定的：旋转、颜色过渡、Reveal/Mask Reveal（clip-path/transform）、逐字出现（文本拆 span + stagger）、聚拢/散开（同一位移原语的时间反向）、镜头推进/拉远/平移（对根容器做 transform）、局部聚焦（裁切副本 + 放大 + 背景压暗）。
**判据：凡是「transform / opacity / clip-path / color」能表达的，都稳定、确定、可逐帧复现。**

### 2. 成本非常低的能力

上一条全部。它们只改合成参数，不改栅格化负载，对渲染耗时影响在噪声级（±几秒）。

### 3. 渲染成本较高的能力

| 能力 | 成本来源 | 程度 |
|---|---|---|
| 大面积 blur / 毛玻璃 | Chromium 每帧重栅格化 | 高，且内存上跳 |
| 嵌入用户视频（video-in-video） | offthreadVideo 抽帧 + 内存 | 中高 |
| 3D（three.js） | WebGL 软渲染 | 高，复杂度也高 |
| SVG 复杂路径形变/手绘任意文字 | 路径数据 + 每帧计算 | 中 |
| 高频 shake 作用于整张大图 | 每帧重采样 | 中低 |
| 超多元素同屏（>50 个独立动画） | 合成树规模 | 中低 |

注：即使「高」，在 10–30s 片段 + 20 分钟容忍线下也不构成否决，只构成「少用/慎用」。

### 4. 兼容/稳定性风险清单

- **backdrop-filter**：headless Chromium 历史 bug 多 → V1 禁用毛玻璃。
- **时间驱动动画**（requestAnimationFrame / Date.now / setTimeout）：破坏逐帧确定性，预览与成品必然不一致 → 一律 `useCurrentFrame()`。
- **Math.random()**：每帧结果不同 → 用 Remotion 的 seed 化 `random()`。
- **外部字体/图片 CDN**：渲染时网络失败 = 任务失败 → 字体打包进仓库（已做），图片走 public/ 静态文件。
- **vw/vh/百分比布局 + devicePixelRatio**：预览与渲染视口差异 → 固定 px 画布（已做）。
- **emoji**：各平台字体不一 → 若需要，用图片 emoji。
- **大图原图直接进场**：用户上传 4000px+ 原图会显著拖慢栅格化 → 上传后先做一次尺寸规整（建议最长边 ≤2560px，质量无损感）。

### 5. 适合图片局部动画的能力

Pop、位移、淡入淡出、强调描边、下划线生长、drawLine、悬浮、局部聚焦放大、依次出现、轻 shake（克制）。
**已验证的关键技法**：平面图片没有分层，「区域独立动画」= 全图打底 + 区域裁切副本做动画；底色块遮蔽法对扁平设计图（Chen 的典型素材）已实测成立。

### 6. 适合信息动画的能力

顺序出现、连线生长（流程箭头）、强调脉冲/高亮、数字滚动、对比布局滑入、发散/汇聚（N 个元素向心/离心位移）、下划线/标记笔、镜头在密集信息图各区域间聚焦移动。

### 7. 两边可复用的能力

**Layer 1 全部原语两边通用**——这正是「统一 Spec」成立的依据：Layer 2 的信息结构（对比/流程/发散…）只是同一批原语的不同编排，不需要为每个结构单独发明动画。工程上 = 一个通用原语解释器 + 若干结构编排器。

### 8. 建议 V1 暂时排除的能力

- 3D / three.js；任意形状 morph；粒子/物理系统
- 毛玻璃/backdrop-filter；大面积动态 blur
- 用户视频嵌套（V1 输入只有图片和文字）
- 音频驱动动画（V1 无音频）
- AI 生成式内容（已明确排除）
- SVG 任意文字手写动画（成本/复杂度不成比例；直线/简单曲线 drawLine 已覆盖「画出来」的感觉）

### 9. 统一 Animation JSON 的设计建议

```jsonc
{
  "spec": "motion-spec@1",            // 版本号，向前兼容的保险
  "canvas": { "width": 1920, "height": 1080, "fps": 30 },
  "durationSec": 10,
  "style": { "accent": "#e8a33d", "font": "NotoSansSC" },
  "elements": [                        // 场景里有什么（声明式，无代码）
    { "id": "title", "type": "text",  "rect": [160,150,900,120], "props": {...} },
    { "id": "img",   "type": "image", "rect": [0,0,1920,1080],   "props": {"src":"..."} }
  ],
  "timeline": [                        // 谁在什么时候做什么动作
    { "at": 0.0, "target": "title", "action": "popIn",      "dur": 0.6 },
    { "at": 0.8, "target": "card3", "action": "slideUp",    "dur": 0.5 },
    { "at": 1.6, "target": "kw",    "action": "highlight",  "dur": 0.8, "params": {"color":"accent"} }
  ]
}
```
要点：
- **action 是封闭枚举**（原语清单），渲染器是通用解释器：`(target, action, params) → Remotion Sequence + spring/interpolate`。AI 和 UI 都只能调用枚举内的能力——这直接实现「AI 不能生成系统不存在的能力」。
- 坐标用相对画布的像素 rect；图片区域另存相对图片的归一化坐标（分辨率无关）。
- 建议 timeline 再分组为 **beats**（开场/展开/强调/收尾），对 AI 的「节奏感」和用户口播结构都更友好（见 15）。
- JSON Schema 强校验：不合法直接拒绝并返回错误原因（给 AI 自我纠正用，也给 UI 表单用）。

### 10. 预览 = 成品的保证机制

现状已是结构保证：预览（@remotion/player）与渲染（renderMedia）用**同一组件 + 同一 JSON + 同一打包字体**，CI 里已做 preview-build 校验。
建议再加一道便宜的保险：**CI 黄金帧**——固定帧渲染 PNG 与仓库基线像素对比，任何「预览改了渲染没改」的漂移当天暴露。成本每次运行 <10s。

### 11. 图片局部框选后最简单稳定的实现

两种模式，按效果类型自动分流：
- **叠加式（默认，最稳）**：原图不动，框选区域的裁切副本叠在上面做动画。适用于 pop/highlight/underline/float/shake/强调——原元素本来就该留在原地，无需遮蔽。零风险。
- **遮蔽式（需要时）**：底色块先盖住原区域，副本再演。适用于「元素入场/移出」类。底色从框选边缘自动采样（或用户点一下取色）。对扁平设计图实测有效（PoC 即此法）；对照片类复杂背景明确告知「入场类效果不适用，改用叠加式强调」。
V1 不做：让用户手动擦除/分层原图（成本高、收益低）。

### 12. 纯 Remotion 就够的效果

Layer 1 全部 + Layer 2 全部。Chromium 的合成器就是我们的动画引擎。

### 13. 还需要 FFmpeg 动画层吗

**V1 不需要。** 纯 FFmpeg（zoompan/overlay）虽更快更省，但会成为第二套动画系统：预览语义不同、Spec 要分裂、「预览=成品」被破坏——为一个不存在的问题（渲染成本）付出架构代价。FFmpeg 留在它现在的位置：Remotion 内部的最终编码器。仅当未来真实渲染耗时成为问题时重议。

### 14. 为 AI 导演预留的结构

- **Spec 即契约**：AI 只输出 spec JSON，Schema 校验不过就打回（附错误原因，支持自我纠正）。
- **能力注册表**：一份机器可读的「原语 + 结构 + 参数约束」清单，直接作为给 LLM 的菜单——规则文档和能力清单是同一份数据，不会脱节。
- **理解与排版分离**：AI 负责「这段在说什么、选什么结构、上哪些信息、强调什么」；**坐标和间距由确定性排版引擎算**（网格 + 安全区 + 字宽测量）。V1 阶段不要让 AI 输出像素坐标——这是防「AI 幻觉坐标」最有效的一刀。
- **人机回环比 AI 更重要**：AI 出 spec → 用户预览确认/微调 → 再渲染。Spec 可编辑意味着用户永远有兜底，AI 失败不等于工具失败。
- **数据资产**：每次「输入 → 采纳的 spec」都存下来，是未来规则引擎/小模型的训练集。

### 15. 「基础动作 → 信息结构 → AI 编排 → Remotion 执行」的架构评估

**思路成立，且与渲染器实现方式同构（通用原语解释器 + 结构编排器），没有架构性错误。** 四个提醒：
1. **防 Spec 膨胀**：V1 的 action/结构清单要小而封闭，扩展走版本号升级，不要为一个案例加一个特例字段。
2. **难点不在动画在排版**：发散/汇聚/层级这类结构的自动化布局（N 个节点怎么摆才好看）是这套系统里真正的新工作量，预算时间请给排版引擎，而不是给动画效果。
3. **AI 不碰坐标**（见 14）：AI 选结构与内容，引擎定位置——把最容易幻觉的部分从 AI 手里拿掉。
4. **beats 层值得加**：timeline 按叙事节拍分组，AI 编排和用户审阅都更符合「这段口播先说什么后说什么」的直觉。

---

## 一句话总结

**技术侧没有红灯。** Layer 1 全部能力已被 PoC 验证或可由已验证原语直接推导；真正需要设计投入的是统一 Spec 的字段边界和结构编排的排版引擎。建议动画能力库按「原语 ≈ 15 个以内、结构 ≈ 首批 4–6 种」起步，Spec 版本化演进。
