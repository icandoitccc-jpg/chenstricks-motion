# Motion 视频策划与交接规范 V0.1.1

适用位置：Motion 项目内的「画面安排 → 导入制作总表」。这不是「素材工具 → 文字图解动画」的独立图解方案格式。

获取入口：Motion「制作规范」页面，或只读 MCP 的 `list_guides` / `read_guide`。规范读取不等于读取用户私人项目；最终稿仍由用户在对话中提供。

## 给新对话的任务

请根据用户提供的最终口播稿，独立策划可由 Motion 执行的视频画面，交付一份制作总表 JSON、简短自查结果及待补素材清单。先阅读本规范，再判断稿子的重点和叙事节奏。不要询问用户的 Motion 项目编号、版本或所谓“制作资料”。不要假装访问过 Motion、Workspace 或 WorkPrint。

本规范不是某篇稿子的标准答案；不要预设幕数、画面比例、录屏数量或总时长。不需要参考上一位 Agent 的总表。

## 1. 先独立判断，再编排

1. 确认拿到的是最终稿，明确该稿的表达目标、受众、语气和论证转折。用户已给出的信息不要重复索取。
2. 按意思与视觉任务分幕，不按 PDF 行数或每句机械切镜。长解释可用多幕展开，连续论证可共享一幕；不能为了凑数量重复做卡片。
3. 优先用可核实的实际操作解释案例；没有实际文件时，只能提出具体的待录制方案，不能写成已经取到素材。不要为了“动态”滥用昂贵生成视频。
4. 让图解承担对比、步骤、要点或强调的任务；画面文案提炼信息，不整段照搬口播，也不把推论改写成用户事实。
5. 对每幕给出可执行的画面、对应原文、所需素材、准备成本与替代方式。只把 Motion 能执行的参数写入执行字段。额外拍摄建议、来源说明属于备注，Motion 不会自动执行。

## 2. 谁做什么，何时需要录音

| 环节 | 责任方 | 输入与输出 |
|---|---|---|
| 定稿 | 用户与 ChatGPT | 用户确认的最终文字 |
| 策划 | ChatGPT 或其他 Agent | 根据最终文字生成本规范的 JSON；使用该 Agent 的订阅额度 |
| 导入检查 | Motion 普通程序 | 核对全文、结构、编号、覆盖及素材引用；自动绑定当前项目；不调用 AI |
| 录音与同步 | 用户录音；Motion 接收时间 | 画面策划无需录音；预览/渲染需要真实时间。目前依赖文字一致的时间字幕或手工标记，自动对齐未完成 |
| 取材 | Agent 选择与核实，用户或已授权工具交接文件 | Workspace 是文字/文件依据，不是视频库。Motion 规范只读 MCP 已提供；WorkPrint 自动取材及 Motion 项目/媒体读写 MCP 尚未接通 |
| 预览与渲染 | Motion 程序执行 | 缺时间或文件的段落不得冒充就绪；云端用量受账户免费配额限制，不是无限免费 |

录音只需先交给 Motion。策划 Agent 不必再收一遍录音；如果后续另请 Agent 负责听音对齐，该阶段才需要录音或真实字幕，并另行说明如何交接。策划稿的 start/end 一律为 null，不按字数、预估语速或“约13分钟”填写秒数。

## 3. 当前能执行的画面

| kind | 能力 | 限制 |
|---|---|---|
| info | 程序文字图解 | template 只支持 focus、steps、comparison、list；不生成任意HTML/JS，不自由绘制复杂关系图 |
| image | 已有图片的静止、轻推或平移 | motion 只支持 still、push、pan；这是整图动效，不能指定“只让图片某区域动” |
| video | 已有录屏/视频按入点播放 | 需要真实文件；sourceIn 是原文件入点秒数。此阶段尚无录音，默认0，不猜应截多少秒 |

focus 强调一个主题，可有1—6项短文字；steps 依次出现步骤；list 展示要点；comparison 左右对比，items 必须恰好两项，并填写 leftLabel/rightLabel。每幕最多6项，建议更少；标题与条目应短而清楚。不同模板的视觉变化有限，不应承诺自定义动画。

独立图片局部动画工具与独立六结构图解工具，不会自动执行项目总表中任意局部指令。当前也未一键互通；不要把它们当成项目模板。

## 4. 可直接导入的格式

输出 UTF-8 的纯 JSON 文件，不加代码围栏、注释、尾随逗号或省略号。用户将它拖入项目的「导入制作总表」。

顶层：
- version：固定1。
- binding：固定 "script"。
- sentences：按全文顺序排列的完整原文单元，1—5000个。可按语义拆分并合并 PDF 断行，不能删改原文和标点。
- assets：图片/视频文件清单；没有就填 []。
- scenes：按视频顺序排列的1—500幕。
- 不提供 projectId、audioRevision、scriptRevision。它们由 Motion 在匹配原文后关联，Agent 不得编造或索取。
- 可加 planningNotes 字符串数组，记录整体风险；可在场景加 recordingInstructions、fallback、sourceStatus 等说明，但它们不属于 Motion 自动执行能力，界面也未保证显示这些备注。

原文单元：
- id：唯一字符串，仅英文字母、数字、下划线和连字符，1—80字符。
- text：非空原文。所有 text 按顺序拼接后，必须与用户终稿完全一致；只允许空格与换行差异。不得统一标点、替换同义词、简繁转换或改写“更通顺”。
- start、end：本阶段必须显式为 null。

每幕：
- id：唯一，规则同原文编号。
- title：1—200字，写有意义的画面主题；实际标题应简短。
- sentenceIds：引用连续原文单元，按原文顺序排列。全文每个单元恰好出现一次；幕与幕顺序不能倒置。
- kind：info / image / video。
- template：focus / steps / comparison / list。图片/录屏可统一填 focus。
- items：字符串数组。info 为1—6项非空文字；comparison恰好2项。图片/录屏可为 []。
- leftLabel、rightLabel：左右标签；非对比幕也可填“之前”“现在”。
- sourceIn：非负数字；无素材填0。
- motion：still / push / pan；非图片幕填 still。
- focusX、focusY：0—100的数字，通常均为50。
- assetId：image/video必填，必须指向assets中类型匹配的编号；info不填。

素材条目：
- id：唯一，限英文字母/数字/下划线/连字符，建议不超过80字符。
- name：唯一的文件名，不含路径或URL。例如“客户表演示.mp4”。不要把文件地址当成已连接素材。
- kind：image 或 video。
- 已有文件和待补文件都可列清单，但必须在交付说明中区分。待补文件导入后仍然缺素材，不能直接渲染该幕。
- 建议图片PNG/JPG/WebP，视频MP4。避免私有客户、账号、邮件及未授权内容入镜；可以明确安排合成示例，但不能冒充历史证据。

### 中性格式示例（仅演示结构，不是用户稿件的策划答案）

```json
{
  "version": 1,
  "binding": "script",
  "sentences": [
    {"id":"S001","text":"今天重复整理表格。","start":null,"end":null},
    {"id":"S002","text":"想把它变成一键操作。","start":null,"end":null}
  ],
  "assets": [],
  "scenes": [
    {
      "id":"SC001",
      "title":"想改变的操作",
      "sentenceIds":["S001","S002"],
      "kind":"info",
      "template":"comparison",
      "items":["重复整理","一键完成"],
      "leftLabel":"现在","rightLabel":"希望",
      "sourceIn":0,"motion":"still","focusX":50,"focusY":50
    }
  ]
}
```

## 5. 不把新风险藏起来

- 没有完整终稿：只索取最终稿，不要求用户导出 Motion 内部资料。
- PDF有页码、标题、篇幅说明：检查它们是否混入提取文字。不能擅自删除后声称可匹配现有项目；策划阶段保留原文并注明“非朗读版式文字待在同步前处理”。不要要求用户把页码读进录音，也不要声称该同步问题已实现。
- 看不到素材：标记待补，写明确录屏动作和无素材替代方案。若实际案例依赖核验，不虚构Workspace记录或WorkPrint视频。
- 需要未实现的画面：改用现有图解/实录，或标成未来建议，不把任意导演指令塞给执行器。
- 导入失败：报告是哪一幕/字段/原文差异；不要随意删除原文、填假时间或换项目编号来绕过校验。
- 尚未验证的混合成片、页面视频回传或10—20分钟渲染：明确待验，不把总表导入成功当成完整视频成功。

## 6. 交付前自查

必须交付：
1. 制作总表JSON文件（全文，不是节选/占位）。
2. 简短摘要：幕数，各kind数量，待补素材及原因；不提供虚构秒数。
3. 已查项目：原文一致、全部覆盖、无重复引用、连续且顺序正确、模板可执行、素材引用完整、时间均null。
4. 仍未查项目：没有实际文件/录音/浏览器或代码执行能力时，明确说明。未经运行不得说“已通过Motion测试”。

有代码环境时，用项目内 scripts/validate-production-plan.mjs 对原文TXT和JSON执行真实导入校验：在项目根目录运行 `node scripts/validate-production-plan.mjs --script 最终稿.txt --plan 制作总表.json`。需先安装 app/package.json 的依赖。没有执行环境就按规范自查并标注“未运行程序校验”。

## 7. 新方案的验收与比较

先过硬性门槛：格式、全文一致与唯一覆盖、支持的模板/参数、素材引用和时间规则。未过门槛先修复，不凭“画面创意好”算可执行。

再比较内容质量：是否抓住表达重点；画面是否补充口播而非照稿念；关键案例是否具体真实；图解/录屏节奏是否合适；需要用户准备多少材料；缺素材是否有可执行替代；哪里比另一份更清楚，哪里更费力。

不把任何旧总表当标准答案，不因幕数相同、图解更多或录屏更多加分，不强求某一比例。分别列“导入已验证”“渲染待验证”“编辑判断”，不混为一个总分。初版规则需随真实测试修订，不宣称已经完成跨Agent验收。
