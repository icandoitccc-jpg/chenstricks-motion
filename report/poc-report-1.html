项目实测 / 推算

单条成片的真实成本模型装环境 ~15s（缓存后更低）+ 渲染 ~15-25s（10-15s 素材）→ 每条约 1 分钟计费

Cloud Run 对照（未开户，理论值）单次 ≈ 45 vCPU·s + 54 GiB·s，对照免费层（18万 vCPU·s / 36万 GiB·s 每月）理论上限数千次/月——额度同样宽裕，但需绑卡开户
结论：按 Chen 的真实用量（每周 ≤1-2 期视频、每期 10-30 个片段），GitHub Actions 免费额度绰绰有余，可以长期 $0 运行，无需 Cloud Run。

三、关键发现（改变原方案判断的）

① 渲染比预想快得多：2 核低配 runner 上 10 秒 1080p30 仅需 ~15s 渲染。瓶颈根本不在渲染，而在装环境（~15s）。「生成要等很久」的担心不成立，正常任务 1-2 分钟内出片，远好于预设的 20 分钟容忍线。
② 内存 ~2GB：并发 2 时峰值 ~2GB。将来若迁 Cloud Run，免费层 2GB 内存实例会偏紧（需 concurrency=1 或 4GB 实例）；Actions 的 7.8GB 无压力。
③ 预览=成品有结构保证：预览与渲染共用同一组件、同一 JSON、同一捆绑字体文件（Noto Sans SC 打包进仓库，不依赖 CDN）。
④ 失败率 0：两个 job 首跑即成功，无 sandbox/字体/权限问题——ChatGPT 预警的「容器中文字体」「Chromium 稳定性」两大坑，被「字体打包 + Remotion 官方浏览器管理」直接绕开。

四、过程问题记录

· 本地：TS 的 interface 不满足 Remotion 泛型约束 → 改 type alias（云端首跑前已拦截）；
· 运维：两个 job 产物同名，解包到同一目录会互相覆盖 → 已改为分目录解包（工程层面后续在产物名中加 job 前缀）；
· 环境：WorkBuddy 平台会将对话/命令中内联的 token 替换为伪值（安全机制），故凭据一律走「文件读取」，已验证可行；
· 云端：0 失败，无需重试。
