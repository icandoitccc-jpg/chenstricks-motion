CHENSTRICKS MOTION · PHASE 2 INPUT

Animation Capability Technical Review

2026-09-21 · 基于已验证栈：Remotion 4.0.526 + GitHub Actions（2 vCPU/7.8GB）+ Q4 输出基准 · 只评估，不实现
性能基线：10s/1080p30 成片云端渲染 ≈ 15–20s，峰值内存 2.4GB，job 墙钟 <70s，用量 ≤几十条/月。即使场景复杂度提升 3–5 倍仍在宽松区间内——性能不是 V1 的约束，简单与稳定才是。

1–2 · 能稳定实现的能力 & 成本

PoC 已实跑验证：淡入淡出 · 位移 · 缩放/Pop（spring）· 悬浮循环 · 描边强调 · 下划线/直线生长（clip-path）· 顺序出现。
同类可直接推导且同样稳定：旋转 · 颜色过渡 · Reveal/Mask Reveal · 逐字出现（拆 span+stagger）· 聚拢/散开（位移原语反向）· 镜头推进/拉远/平移（根容器 transform）· 局部聚焦（裁切副本放大+背景压暗）。
判据：凡 transform / opacity / clip-path / color 能表达的，都稳定、确定、可逐帧复现，且渲染成本在噪声级（±几秒）。

3 · 渲染成本较高的能力

能力成本来源程度
大面积 blur / 毛玻璃每帧重栅格化高，内存上跳
嵌入用户视频offthreadVideo 抽帧+内存中高
3D（three.js）WebGL 软渲染高，复杂度也高
SVG 复杂路径形变 / 任意文字手写路径数据+每帧计算中
整张大图高频 shake / 超50个同屏动画重采样 / 合成树规模中低
即使「高」，在 10–30s 片段 + 20 分钟容忍线下也只构成「少用」，不构成否决。

4 · 兼容 / 稳定性风险清单

· backdrop-filter：headless Chromium 历史 bug 多 → V1 禁用毛玻璃；
· 时间驱动动画（rAF / Date.now / setTimeout）：破坏逐帧确定性，预览≠成品 → 一律 useCurrentFrame()；
· Math.random()：每帧结果不同 → 用 Remotion seed 化 random()；
· 外部字体/图片 CDN：渲染时网络失败=任务失败 → 字体打包（已做）、图片走 public/ 静态文件；
· vw/vh + devicePixelRatio：预览与渲染视口差异 → 固定 px 画布（已做）；
· emoji：平台字体不一 → 需要时用图片 emoji；
· 超大原图：4000px+ 原图拖慢栅格化 → 上传后先规整到最长边 ≤2560px。

5–7 · 两个功能的适用能力 & 复用

图片局部动画：Pop · 位移 · 淡入淡出 · 强调描边 · 下划线生长 · drawLine · 悬浮 · 局部聚焦放大 · 依次出现 · 轻 shake（克制）。关键技法已验证：平面图片无分层，「区域独立动画」= 全图打底 + 区域裁切副本做动画。
信息动画：顺序出现 · 连线生长 · 强调脉冲/高亮 · 数字滚动 · 对比布局滑入 · 发散/汇聚 · 下划线/标记笔 · 镜头在信息图各区域间聚焦移动。
复用结论：Layer 1 全部原语两边通用——Layer 2 信息结构只是同一批原语的不同编排。工程上 = 一个通用原语解释器 + 若干结构编排器。这正是统一 Spec 成立的依据。

8 · 建议 V1 暂时排除

3D/three.js · 任意形状 morph · 粒子/物理系统 · 毛玻璃/大面积动态 blur · 用户视频嵌套（V1 输入只有图片和文字）· 音频驱动动画 · AI 生成式内容 · SVG 任意文字手写（直线/简单曲线 drawLine 已覆盖「画出来」的感觉）。

9 · 统一 Animation JSON 建议

{
  "spec": "motion-spec@1",  // 版本号，向前兼容的保险
  "canvas": { "width": 1920, "height": 1080, "fps": 30 },
  "durationSec": 10,
  "style": { "accent": "#e8a33d", "font": "NotoSansSC" },
  "elements": [ // 场景里有什么（声明式，无代码）
    { "id": "title", "type": "text", "rect": [160,150,900,120], "props": {...} }
  ],
  "timeline": [ // 谁在什么时候做什么动作
    { "at": 0.0, "target": "title", "action": "popIn", "dur": 0.6 },
    { "at": 1.6, "target": "kw", "action": "highlight", "dur": 0.8 }
  ]
}
· action 是封闭枚举：渲染器是通用解释器 (target, action, params) → Sequence + spring；AI 和 UI 都只能调用枚举内能力——直接实现「AI 不能生成系统不存在的能力」。
· 图片区域存相对图片的归一化坐标（分辨率无关）；timeline 建议分组为 beats（开场/展开/强调/收尾）。
· JSON Schema 强校验：不合法直接打回并附错误原因（给 AI 自我纠正、给 UI 表单用）。

10 · 预览 = 成品的保证

已是结构保证：预览与渲染同一组件 + 同一 JSON + 同一打包字体，CI 已做 preview-build 校验。建议再加一道便宜保险：CI 黄金帧——固定帧渲染 PNG 与基线像素对比，任何漂移当天暴露（每次 <10s）。

11 · 图片局部框选的最稳实现

两种模式按效果自动分流：
叠加式（默认，零风险）：原图不动，框选区域裁切副本叠在上面做动画。适用 pop/highlight/underline/float/shake——原元素本来就该留在原地，无需遮蔽。
遮蔽式（需要时）：底色块盖住原区域，副本再演。适用「元素入场/移出」。底色从框选边缘自动采样（或用户点取）。对扁平设计图实测有效（PoC 即此法）；照片类复杂背景明确提示改用叠加式。
V1 不做：让用户手动擦除/分层原图。

12–13 · Remotion 边界 & FFmpeg 定位

Layer 1 + Layer 2 全部纯 Remotion 就够，Chromium 合成器就是动画引擎。V1 不需要 FFmpeg 动画层——它会变成第二套动画系统，破坏统一 Spec 与「预览=成品」。FFmpeg 留在现在的位置：Remotion 内部的最终编码器。仅当真实渲染耗时成为问题时重议。

14 · 为 AI 导演预留的结构

· Spec 即契约：AI 只输出 spec JSON，Schema 校验不过就打回（附原因，支持自我纠正）；
· 能力注册表：机器可读的「原语+结构+参数约束」清单，直接作为给 LLM 的菜单——规则文档和能力清单是同一份数据，不会脱节；
· 理解与排版分离：AI 负责「在说什么/选什么结构/上哪些信息/强调什么」；坐标间距由确定性排版引擎算（网格+安全区+字宽测量）。V1 不要让 AI 输出像素坐标——这是防幻觉坐标最有效的一刀；
· 人机回环比 AI 更重要：AI 出 spec → 用户预览确认/微调 → 渲染。Spec 可编辑意味着 AI 失败≠工具失败；
· 数据资产：每次「输入 → 采纳的 spec」存档，是未来规则引擎/小模型的训练集。

15 · 「基础动作→信息结构→AI编排→Remotion执行」架构评估

思路成立，与渲染器实现方式同构（通用原语解释器+结构编排器），无架构性错误。四个提醒：
① 防 Spec 膨胀：V1 的 action/结构清单小而封闭，扩展走版本号，不为单个案例加特例字段；
② 难点不在动画在排版：发散/汇聚/层级的自动化布局（N 个节点怎么摆）是真正的新工作量，时间预算给排版引擎而不是动画效果；
③ AI 不碰坐标（见 14）；
④ beats 层值得加：更符合口播「先说什么后说什么」的直觉，AI 编排和用户审阅都受益。
一句话总结：技术侧没有红灯。Layer 1 全部能力已被 PoC 验证或可由已验证原语直接推导；真正需要设计投入的是统一 Spec 的字段边界和结构编排的排版引擎。建议能力库按「原语 ≤15 个、结构首批 4–6 种」起步，Spec 版本化演进。
